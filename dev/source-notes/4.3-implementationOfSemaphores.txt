4.3 Implementation of semaphores
Hardware support for synchronization
Most contemporary computer architectures offer hardware support for process synchronization in the form of specialized machine instructions.

The test-and-set instruction (TS) copies a variable into a register and sets the variable to zero in one indivisible machine cycle. Test-and-set has the form TS(R, x) where R is a register and x is a memory location and performs the following operations:

Copy x into R
Set x to 0
A lock is a synchronization barrier through which only one process can pass at a time. TS allows an easy implementation of a lock.

Captions
Two processes, p1 and p2, share a lock, implemented using a TS instruction on a shared variable x. R1 is a register of p1 and R2 is a register of p2.
Initially, x = 0, implying that neither process may pass the lock. The initial values of R1 and R2 are irrelevant at this time.
Process p1 executes TS, which copies x into R1 and sets x = 0. Since R1 remains 0, p1 continues executing the while-loop repeatedly.
Similarly, the TS of p2 copies x into R2 and sets x = 0. Since R2 is 0, p2 also keeps executing the while-loop repeatedly.
Both p1 and p2 are waiting inside the respective while-loops for the lock to open.
Later a third process p3 opens the lock by writing a 1 into x.
Whichever process reaches TS first, copies the 1 into the register and sets x back to 0. Here p1 executed TS first.
Since R1 = 1, process p1 passes the lock and continues with the next instruction while process p2 remains in the while-loop executing TS.

Binary semaphores
Many synchronization problems do not require the full power of a general semaphore.

A binary semaphore can take only the values 0 or 1. Pb and Vb are the simplified P and V operations that manipulate binary semaphores. Pb and Vb on the binary semaphore sb can be implemented directly using the TS instruction:

Vb(sb): sb = 1
Pb(sb): do TS(R,sb) while R == 0
Busy-waiting is the act of repeatedly executing a loop while waiting for some condition to change. Busy-waiting consumes CPU resources and should be avoided whenever possible. The implementation of Pb(sb) using TS is very simple but suffers from the drawback of busy-waiting.

Captions
The single semaphore used in the CS problem never exceeds the value 1. Therefore, a binary semaphore, mutex, with the corresponding Pb and Vb operations, is sufficient to solve the problem.
Only one process at a time can pass the Pb(mutex) operation.
If p1 enters, p2 remains blocked until p1 executes Vb(mutex).
When p1 executes Vb(mutex), p2 can enter CS.
In the bounded buffer problem, if the buffer consists of only a single slot, then two binary semaphores, empty and full, are sufficient.
Initially, empty is 1 and full is 0. Thus only the producer can continue while the consumer is blocked.
When data has been placed into the buffer, full becomes 1 and the consumer can continue while the producer is blocked.

Implementing P and V operations on general semaphores
A general semaphore s can be implemented using a regular integer variable manipulated by the functions P(s) and V(s). To guarantee that only one operation at a time can access and manipulate s, a binary semaphore is used.

The variable s serves a dual purpose:

When s is greater or equal 0, s represents the value of the semaphore.
Whenever s falls below 0, the absolute value of s represents the number of processes blocked on the semaphore.
To avoid busy-waiting inside P(s) when s falls below 0, the process performs a blocking request, which places the process on a waiting list associated with s. A V(s) operation increments s and reactivates one process if one or more are blocked on s.

Captions
The implementation of P and V uses an integer s to represent the semaphore. A waiting list is associated with s, where blocked processes wait for s > 0.
P(s) decrements s in a critical section implemented using the binary semaphore ms. If s < 0, the process blocks itself after releasing the critical section.
V(s) increments s in a critical section implemented using the same semaphore ms. If s <= 0 then one or more processes are blocked on s. One process is reactivated, still in critical section.
If s = 1 initially, a process p1 decrements s. Since s is not less than 0, the process completes the P operation and leaves.
If p1 repeats the same P operation, s becomes -1, and the process blocks itself on s. The value s = -1 indicates that 1 process is blocked.
When another process, p2, tries to pass the P operation, s is again decremented and p2 becomes blocked on s. The value s = -2 indicates that 2 processes are blocked.
A subsequent V operation increments s. Since s is less than or equal 0, V reactivates p1 from the waiting list, which exits the critical section and continues executing.
Another V(s) operation reactivates p2, leaving the waiting list empty and the semaphore equal to 0.
One more V(s) operation only increments s again but no process is reactivated.

Note on implementation issues
The implementation is only in pseudocode, which hides a number of subtle details. In particular, the function “reactive a process” may have to wait for a process to be on the waiting list, even though s <= 0. The situation can occur when a context switch happens just after the instruction Vb(ms) in P(s) but before “block self on s” had a chance to place the process on the waiting list. Another common solution to the problem is to disable interrupts during the execution of the P and V operations.

1)
Allowing the variable s to become negative violates the definition of a semaphore.
2)
s can be initialized to any integer value.
3)

4)
s = 0 implies that the waiting list on s is empty.
5)
The waiting list of processes blocked on a semaphore can become arbitrarily long.
6)
Decrementing and testing s in P(s) is a critical section.
7)
The operation Vb(ms) in P(s) could safely be moved after the operation "block self on s".
