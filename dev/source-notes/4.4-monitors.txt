4.4 Monitors
P and V operations on general semaphores are versatile primitives capable of solving a variety of synchronization problems. But P and V operations are low-level primitives that are prone to difficult-to-diagnose programming errors.

Basic principles of monitors
A monitor is a high-level synchronization primitive implemented using P and V operations. Following the principles of abstract data types, a monitor encapsulates data along with functions through which the data may be accessed and manipulated.

A condition variable is a named queue on which processes can wait for some condition to become true.

The implementation of a monitor must:

guarantee that the functions are mutually exclusive. Thus only one process at a time may be executing inside a monitor.
provide condition variables such that a process can step outside of the monitor while waiting for a condition and thus not prevent other processes from entering the monitor.
A condition variable c is accessed using two special operations:
c.wait causes the executing process to block and be placed on a waiting queue associated with the condition variable c.
c.signal reactivates the process at the head of the queue associated with the condition variable c.

Captions
A monitor M has an internal variable x and 2 functions, f and g.
A process entering the monitor by calling M.f() must wait for x to be positive before proceeding. A condition variable x_is_positive is defined for that purpose.
Process p1 calls M.f() and finds x = -1. Executing "x_is_positive.wait" blocks the process on the condition variable.
When another process p2 calls M.g() and sets x = 5, the condition is satisfied and the statement "x_is_positive.signal" reactivates the blocked process p1.
Now p1 can resume executing f and p2 can continue executing g. But the monitor definition stipulates that only one process may execute inside the monitor.
The semantics of signal grant the blocked process p1 the right to continue immediately while the signaling process p2 becomes blocked in a high-priority queue called urgent.
When p1 exits the function f, the blocked process p2 is reactivated and can complete the function g.

A monitor implementation of the bounded-buffer problem
The monitor primitive offers a simple solution to the bounded-buffer problem. Since the monitor guarantees mutual exclusion, the functions to deposit and to remove data automatically become critical sections. Consequently, the solution works for multiple producers and multiple consumers.

The condition notfull is used by the producer to wait when all buffer slots are full. Analogously, the condition notempty is used by the consumer to wait when all buffer slots are empty.

A counter, full_slots, initially set to 0, is used to keep track of how many slots are full. The counter is incremented by the producer and decremented by the consumer during each call to the monitor.

Captions
The buffer is an array accessible via the functions deposit and remove. Initially, all slots are empty (full_slots = 0)
If a consumer process c1 calls remove(), then c1 becomes blocked on the notempty condition.
A producer process p1 calls deposit(). Since free slots are available (full_slots != n), p1 places the data into the buffer, increments full_slots, and signals any process blocked on notempty.
c1 reenters the remove() function, removes the data from the buffer, decrements full_slots, and signals the notfull queue. Since no process is blocked, the signal has no effect.
If producers run ahead of consumers by n steps then all buffer slots become full. All subsequent producers become blocked on notfull until at least one slot becomes empty again.
A subsequent removal triggers the first blocked producer to reenter and complete the deposit.
As long as full_slots is greater than 0 and less than n, all producers and all consumers will proceed without entering the notfull or notempty queues.

Monitors with priority waits
Normally a queue associated with a conditional variable is processed in FIFO order. Some applications require additional control over the order of process reactivation.

A priority wait has the form c.wait(p), where c is a conditional variable and p is an integer specifying a priority according to which processes blocked on c are reactivated.

 monitor alarm_clock }tick() { now = now + 1wakeup.signal}wakeme(n) {alarm_setting = now + nwhile (now < alarm_setting)wakeup.signal hardware wakeupwakeup.wait(alarm_setting)alarm_setting valuescondition wakeupwakeup.wait11p213p1now = 10;now = 0;now = 11;p311

Captions
A monitor alarm_clock provides a facility for processes to get blocked for n number of time ticks by calling the function wakeme(n). The shared variable now, initially 0, keeps the current time.
A condition variable wakeup is provided for processes to await the time to wake up.
If p1 calls wakeme(3) at time now = 10, then p1's alarm_setting = 10 + 3 = 13. Since now is less than alarm_setting, p1 is blocked on the wakeup queue.
Similarly, if p2 and p3 call wakeme(1) at time now = 10, then p2's and p3's alarm_setting = 10 + 1 = 11. Since now is less than alarm_setting, p2 and p3 are also blocked on the wakeup queue.
A hardware interrupt periodically calls the function tick, which increments the current time, now, by 1. The function then issues a signal to the first process blocked on the wakeup queue.
The problem is that p1 would wake up before p2 and p3, even though p2's and p3's alarm settings are lower (11) than p1's alarm setting (13).
When priority waits are used, where alarm_setting is the priority, all processes are sorted in increasing order of alarm_setting.
The next tick increments now to 11 and the signal reactivates p2. Since now = alarm_setting, p2 exits the while loop and leaves the monitor.
Before leaving the monitor, p2 issues a wakeup.signal to assure that, if the next blocked process (p3) has the same alarm_setting as p2, the process is reactivated before the next tick is called.
p3's alarm setting is equal to now and thus p3 leaves the monitor. p1 awaits 2 more ticks until now = 13.

Implementation of a monitor
A compiler or preprocessor uses P and V operations on semaphores to enforce the different features of a monitor.

A semaphore mutex (initialized to 1) is used to enforce mutual exclusion among the functions.
A semaphore c (initialized to 0) is used for each condition variable c to allow a process to block itself on the condition.
A semaphore urg (initialized to 0) is used to block a process executing a signal operation.
Associated with each semaphore c is a counter c_cnt, which keeps track of the number of processes blocked on c.
Associated with the semaphore urg is a counter urg_cnt, which keeps track of the number of processes blocked on urg.
The compiler then replaces each function body and all wait and signal operations with the corresponding segment of code:

Captions
The compiler is implementing the function deposit() of the bounded buffer monitor.
The compiler first inserts the code to enforce mutual exclusion. P(mutex) guarantees that only one process can be executing the function.
Before exiting the function, the process must release mutex or, if another process is blocked on the urgent queue (urg_cnt > 0), then the blocked process is reactivated using V(urg).
The compiler then replaces the notfull.wait and notempty.signal instructions with the corresponding code segments.

To record that one more process is blocked on the notfull queue, the process increments notfull_cnt prior to blocking itself. When the process resumes, notfull is again decremented.
If a process is waiting in the notempty condition queue (notempty_cnt > 0) then the signaling process reactivates the waiting process and blocks itself on the urgent queue.
The urg_cnt is incremented before the signaling process blocks itself and is again decremented when the process resumes.

4.4.2: Bounded stack monitor.

(a)
Write a monitor to implement a bounded stack, b_stack, which may contain at most max elements. The push and pop operations behave as follows:

stack.push(x): If the stack is not completely full, the operation pushes the new element x on top of the stack. Otherwise, the operation has no effect and the value of x is discarded.
stack.pop(x): If the stack is not completely empty, the operation removes the value currently on top of the stack and returns the value in the variable x. If the stack is empty, the operation waits until a value has been pushed on the stack and then completes the pop.
